## Context

Story generation now runs through Trigger.dev and persists intermediate work in Supabase/Postgres and Storage. The current design is a durable background runner plus idempotent skip-if-exists behavior, not a fully step-checkpointed workflow.

A smoke test showed that successful runs can complete end-to-end, but timeout/cancel paths can leave a story row stuck in `status='generating'` with the last persisted progress step. Trigger.dev max-duration timeouts may not call normal task failure hooks, so the task-level `try/catch` is not sufficient to mark the row failed. The UI then appears to hang because it accurately renders the stale persisted state.

The existing persistence model is still useful: narrative/manifest data and uploaded images are persisted, and rerunning the same story can skip already-uploaded Storage objects. This durable background runner + idempotent skip-if-exists approach is acceptable and should be preserved.

## Goal

Make stale, timed-out, or cancelled story generations recoverable and understandable to users without losing already persisted work.

## Scope

- Detect story rows that remain `generating` beyond an expected freshness threshold.
- Add a user-facing UI state for stale/timed-out generations instead of showing an indefinitely active progress state.
- Persist better failure information for timeout/cancel paths where possible.
- Provide a retry/resume path that re-enqueues the same `storyId` so the pipeline can reuse persisted manifest data and skip already-uploaded images.
- Keep the current durable background runner + idempotent skip-if-exists model; do not require splitting image generation into per-page tasks.

## Acceptance Sketch

- A story whose `updated_at` is too old while `status='generating'` is surfaced as stale/timed-out in the UI with clear copy.
- Retrying a stale story reuses the same `storyId` and does not regenerate already uploaded images.
- Timeout/cancel failures persist a useful error message when the platform gives us a hook or observable signal.
- If direct timeout hooks are unavailable, a watchdog/cleanup mechanism marks stale rows failed or stale after a threshold.
- Users do not see an infinite-progress card for work that is no longer actively running.

## Open Questions

- Should stale rows be marked `failed`, or should we introduce a distinct `stale`/`timed_out` status?
- What freshness threshold should determine stale generation locally and in production?
- Should retry be automatic via watchdog, manual via UI, or both?
- Where should the retry/resume endpoint live: Supabase Edge Function, Trigger.dev task, or another server-side route?
- Can Trigger.dev expose enough cancellation/timeout metadata to persist accurate terminal errors, or do we need a periodic reconciler?
